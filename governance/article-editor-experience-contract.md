# 文脉完整文章编辑器体验合同

版本：`1.1.0-draft`

日期：2026-08-21

状态：实现中的目标合同；只有本文逐项证据齐全后，才能把“完整文章编辑器”标记为完成。

## 1. 产品定义

- 主要用户：维护大量本地文章、版本、研究材料、平台稿和创作规则的单人内容制作人。
- 用户角色：不是在后台填写文章字段，而是在一间可视化内容工坊里拆解、组合、试写、构建和回看自己的文章工程。
- 一句话隐喻：**一篇文章既是可以直接阅读的成品，也是能够安全解包、修改、分支、构建并再次打包的工程文件。**
- 核心承诺：任何进入文脉的文章，都能在不覆盖原文件的前提下变成一个有稳定模块、来源、关系、修订和构建记录的本地工程；工程随时可以编译成读者看到的文章，也可以导出后再次导入继续制作。

明确不要：

- 不把游戏制作名词逐字搬进文章产品；
- 不把表单、状态卡、日志和统计页当成编辑器；
- 不用漂亮但不可操作的假画布、假连线或假进度；
- 不让自动拆解结果冒充人工确认的结构、观点或证据关系；
- 不覆盖用户的历史源文件，也不让 Agent 直接写主分支、批准或发布。

## 2. 核心对象

```text
ArticleProject
  ├─ SourceRef[]                 只读来源与导入证据
  ├─ Branch → WorkingProject     当前可编辑工程
  ├─ Module[]                    标题、段落、论点、证据、引用、列表、媒体、行动等
  ├─ Edge[]                      顺序、支持、反驳、引用、变体等显式关系
  ├─ Composition                 成品顺序、隐藏模块、平台覆盖和渲染设置
  ├─ DiagnosticRun → Issue[]     绑定当前工程快照的问题、证据与处理决定
  ├─ Revision → ProjectSnapshot  不可变工程快照与编译正文
  ├─ Build[]                     完整版、摘要、Demo、切片、平台草稿
  └─ Package                     可导出、可再导入、可验证摘要的工程文件
```

模块与关系由稳定 ID 连接；界面位置、列表序号和标题不能充当对象身份。正文是工程的确定性编译结果，不是另一份需要人工同步的真相。

## 3. 代表旅程

1. 用户从资料库选择历史文章，或导入 `.md`、`.txt`、文脉工程包。
2. 系统先显示来源、格式、摘要和将要创建的对象；分别确认“导入当前文章 / 建立独立文章”的归属与“轻量建档 / 完整生产”的处理预设，再在 D1 建立本地工程，不改原文件。确认前的推荐动作只允许写入防重放幂等回执，不得创建或修改 Article、Branch、Revision、Composition、Package。
3. 确定性拆解器把正文转换为模块和初始顺序关系，同时把“自动推断”标在来源上。
4. 用户在同一工作面使用工程大纲、结构画布和属性检查器选择、重排、新增、复制、隐藏、删除或编辑模块。
5. 成品预览实时从当前模块图编译，不读取另一份手工维护的正文。
6. 保存只更新工作工程；提交会同时冻结模块图、关系、编译正文、摘要和父修订。
7. 用户可以开分支进行另一种结构实验，再用显式差异与人工合并回主线。
8. 用户从同一修订建立完整版、Demo/摘要、宣传切片或平台草稿 Build；Build 记录选择规则和输入摘要。
9. 用户可以下载工程包，并把它重新导入为新工程；往返后正文、模块 ID、关系和摘要保持一致。
10. Agent 读取冻结工程快照，只能提交候选补丁、工件或任务分支修订；人类决定是否应用。
11. 用户可以对当前工程运行确定性门禁、Skill 或外部 AI 诊断；问题必须定位到文章、模块或关系，并形成可追溯的修复补丁，而不是只输出一段聊天建议。

## 4. 桌面代表切片

### 顶部工具条

- 当前工程、分支、基线修订和保存状态；
- `导入`、`保存工程`、`提交修订`、`构建`、`导出工程包`；
- 结构、源码、成品预览和构建四种真实工作模式。

### 左侧：工程大纲

- 按成品顺序显示模块、类型、角色、状态和来源标记；
- 支持搜索、类型过滤、拖动重排、键盘上移/下移、折叠与定位；
- 新增、复制、隐藏和删除必须真的改变工程状态并可撤销或在提交前恢复。

### 中间：结构画布或正文/预览

- 结构画布显示模块节点和显式关系；顺序连线与语义关系视觉上不同；
- 选择节点会同步大纲和检查器；拖动只改变有意义的顺序或布局状态；
- 源码模式是工程编译出的 Markdown，可用于精确校对；
- 成品预览只显示读者会看到的内容，不混入工程元数据。

### 右侧：属性检查器

- 编辑模块类型、角色、标题、正文、状态、标签、来源引用和关系；
- 显示当前字段是导入事实、规则推断、Agent 候选还是人工确认；
- 任何会使旧门禁、批准或 Build 过期的操作，在保存前明确提示影响。

## 5. 输入、输出和可逆性合同

### 输入

- 历史 corpus 版本：以版本 ID、正文 SHA-256 和路径证据绑定；
- 外部 Markdown/TXT：以本次导入工件摘要绑定；
- 文脉工程包：严格校验 schema、对象唯一性、引用完整性和摘要；
- DOCX、网页剪藏和富媒体为后续输入适配器；未实现前不得在界面声称已支持。

### 导入分流与轻量建档

- 文章归属与处理成熟度是两个独立决策轴，不组合成四种身份，也不使用 Package/Branch 的 `active / archived` 状态冒充成熟度；
- LLM 只能推荐 `light_archive / full_production`，返回推荐、置信度、理由和缺失信号；不能选择归属、替用户勾选、确认导入或推进 Article/Revision/Composition；
- 云端模型只接收格式、篇幅、结构、来源/发布提示等脱敏统计，不接收正文、文件名、标题或 SHA；模型未配置、超时或输出不合法时，明确降级为规则建议，人工导入不被阻断；
- 轻量建档仍建立稳定 Article、Branch、Revision、Package、来源指纹和处理决定，但不要求事实台账、封面、DOCX、平台物料或交付回执，也不能声明成稿或发布就绪；
- 完整生产表示进入事实核验、成稿、审校、封面、DOCX、平台适配与交付门禁，不表示这些工件已经完成；
- 选择结果、推荐快照、来源 SHA 与人工覆盖关系进入 `PackageDocument.metadata.importWorkflow`，由 Composition/Document SHA 冻结；
- 导入当前文章时，处理预设只随候选 Patch 保存，人工批准并应用前不能声称当前 Revision 已改变；
- 同一来源身份再次选择不同预设时不得静默复用旧 Package。升级应在同一 Article/Branch 上建立只改元数据的候选 Patch，应用后创建新 Composition 与新 Revision，保留 Article ID。

### 输出

- 编译 Markdown；
- 不可变 ArticleRevision + ProjectSnapshot；
- 文脉工程包；
- 完整、摘要、Demo、宣传切片与平台草稿 Build；
- Agent 候选补丁与人工应用记录。

### 往返验收

同一工程执行 `导出 → 重新导入 → 再编译` 后，必须满足：

- 包 schema 与摘要有效；
- project/module/edge/source 稳定 ID 不丢失；
- 引用全部可解析；
- 编译正文 SHA-256 与导出前一致；
- 隐藏模块、平台覆盖和 Build 选择规则不被悄悄丢弃。

## 6. Agent 合同

- 上下文冻结正文修订、ProjectSnapshot SHA-256、模块图、来源、采用规则、限界知识子图和权限上限；
- Agent 只可读取允许的快照，并追加进度、工件、人工请求、图谱候选或 `ProjectPatch`；
- `ProjectPatch` 必须声明 base project SHA-256、目标模块 ID、操作和预期结果；陈旧基线返回冲突；
- Agent 不能直接写 main、合并、删除源材料、批准内容、批准 Release、执行外部提交或采纳规则；
- Agent 完成只表示候选工件到达人工验收，不代表文章或发行完成。

## 7. 诊断与修复合同

- 每次诊断冻结 Composition/WorkingProject SHA-256、诊断器/Skill ID、版本和参数；工程变化后旧问题标记为过期；
- Issue 至少包含稳定 ID、严重度、问题类型、目标 module/node/edge、解释、证据、建议动作和来源；
- 自动诊断只能产生 `candidate` 问题，不能擅自改正文或宣称问题已解决；
- 用户可以确认、忽略、标记误报、交给 Agent、手工修复或应用候选 Patch；决定进入事件链；
- 修复 Patch 绑定基础工程摘要，并显示会新增、修改、移动或删除哪些模块；应用前必须通过 CAS；
- 应用后重新运行同一诊断，只有新运行不再命中且输入摘要一致，Issue 才能标记为 `resolved`；
- 诊断面板按当前模块、当前章节和全篇三个范围过滤，并可从问题直接定位到画布与检查器。

## 8. MCP 与机器接口合同

- `/.well-known` 发现文件、机器 manifest、JSON Schema、提示词和 MCP server 必须引用同一 ArticleProject 合同；
- MCP 至少提供有界的项目/工程/模块/诊断/Skill/门禁/任务读取，以及候选 Patch、诊断结果、进度和工件写入；
- 每个写工具要求稳定 `commandId`、当前摘要或 lock version、对象范围 token 和明确副作用声明；
- 不同 AI 使用同一对象 ID、schema 和完成状态，不需要依赖站内界面文案或人工复制整篇提示词；
- MCP 不暴露任意 Shell、任意本地文件读取、主分支直写、合并、编辑批准、发行批准或外部发布；
- `tools/list`、资源模板、错误代码、重放、撤销 token、超限和陈旧上下文必须有自动合同与真实 stdio 探针。

## 9. 本地建档与发展树合同

- 资料分类优先读取显式 manifest/metadata/article ID/发布回执，再使用目录、文件名和文本特征；推断必须保留规则、置信度与待人工确认状态；
- 正式发布文章、创作中正文、平台变体、测试/QA、Skill 或工作流总结、研究治理、来源材料和创作工具不能混为同一种“文章”；
- 同一作品的发展树使用稳定关系表达 `derived_from / revision_of / platform_variant_of / excerpt_of / supporting_material_for / test_fixture_for / supersedes`；
- 历史对话只在有可追溯会话/工件引用时作为证据，不根据聊天顺序或标题相似度伪造关系；
- 自动分类和发展树先进入候选覆盖层，人工决定后才能成为本地 D1 的 canonical override；刷新索引不得覆盖人工决定；
- Skill、门禁、模板和检查器继续从本地入口动态索引，网站只保存采用决定、运行和证据，不复制写死能力内容。

## 10. 响应式、键盘和恢复

- 桌面采用大纲—画布—检查器三栏；窄屏重组为可切换的“大纲 / 编辑 / 属性 / 预览”，不把三栏等比压缩；
- 所有拖拽动作必须有按钮或键盘替代；触控目标至少 44×44px；
- `Ctrl/Cmd+S` 保存工程，`Ctrl/Cmd+Enter` 打开提交修订，方向调整必须有可见焦点；
- 提交前的本地修改可恢复；并发 CAS 冲突不得覆盖对方修改；
- 解析、保存、构建、导入和导出失败都保留当前工作并提供可理解的恢复动作；
- 尊重 `prefers-reduced-motion`，结构变化不依赖动画才能理解。

## 11. 完成证据

只有以下证据全部存在，才可称为完整版本：

1. 新库迁移和既有本地 D1 升级探针均通过；
2. 外部 Markdown、历史 corpus 与工程包三条导入路径各有真实 D1 闭环；
3. 模块增删改、重排、关系编辑、保存、冲突、提交、分支和快照均有合同测试；
4. 工程包 round-trip 与五类 Build 的输入/输出摘要测试通过；
5. Agent 冻结工程上下文、陈旧补丁拒绝、候选应用与权限拒绝通过；
6. 1366×768、1440×900、390×844 的真实浏览器旅程通过；
7. 键盘完成导入后的模块选择、重排、保存、预览与提交；
8. 源 corpus 文件哈希在完整验收前后不变；
9. 内容所有者用一篇真实文章走完代表旅程并签发方向和可用性。
10. 当前语料分类抽样逐项核对，正式文章与中间材料不再混放；候选发展树能追溯到规则或显式证据；
11. 诊断 Issue 能定位模块、生成候选修复、CAS 应用并通过同一诊断复验；
12. 两种独立 MCP 客户端完成发现、读取冻结工程、提交候选 Patch/进度和错误恢复，不获得禁止权限。

自动测试、截图和结构检查只能证明各自覆盖的部分，不能替代第 9 项人工签发。
